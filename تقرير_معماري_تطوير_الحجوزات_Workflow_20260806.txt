1.1 هيكل نظام Workflow الحالي
--------------------------------------------------
النظام الحالي يتكون من الجداول التالية في قاعدة البيانات:

  • workflows
    - المعرف: id, name, description, transaction_type, branch_id, default_status_id
    - الغرض: تعريف سير العمل حسب نوع المعاملة
    - أنواع المعاملات الموجودة حالياً:
        1) umrah (تأشيرات العمرة)
        2) work_visa (تأشيرات العمل)
        3) visa (زيارات عائلية)
        4) booking (حجوزات - قديم)
        5) bus_flight_bookings (حجوزات باص وطيران - فعال حالياً)

  • workflow_steps
    - المعرف: id, workflow_id, status_id, step_name, step_key, sort_order
    - خصائص إضافية: is_initial, is_final, is_editable, require_note, require_reason
    - الحقول: required_fields (JSON), show_fields, show_checklist
    - مثال خطوات سير الحجوزات الحالية (workflow_id=5):
        step_id=31: "جديد"        status_id=22  is_initial=1
        step_id=32: "تأكيد الحجز" status_id=25  show_fields=ticket_number,confirm_datetime
        step_id=33: "تم إلغاء الحجز" status_id=26 show_fields=is_cancelled,cancel_reason,cancel_datetime
        step_id=34: "تم تعديل الحجز" status_id=27 show_fields=mod_reason,mod_datetime,discount_amount
        step_id=35: "تم السفر"    status_id=28  is_final=1

  • workflow_transitions
    - المعرف: workflow_id, from_step_id, to_step_id
    - الصلاحيات: role_id (CSV), allow_by_user_id
    - الميزات: require_approval (0/1), auto_action (مثل supplier_credit_posting)
    - مثال الانتقالات الحالية لحجوزات bus_flight_bookings (workflow_id=5):
        T28: 31 → 32  (جديد → تأكيد الحجز)   require_approval=1  auto_action=supplier_credit_posting
        T29: 31 → 33  (جديد → إلغاء)         require_approval=0
        T30: 32 → 33  (تأكيد → إلغاء)        require_approval=0
        T31: 32 → 34  (تأكيد → تعديل)        require_approval=1
        T33: 34 → 32  (تعديل → تأكيد)        require_approval=0
        T35: 32 → 35  (تأكيد → سافر)         require_approval=0

  • workflow_approval_requests
    - المعرف: request_number, passport_id, booking_id
    - الانتقال: from_step_id → to_step_id
    - الطلب: requested_by, requested_role_id, notes, admin_notes
    - المالية: payment_id, extra_data (JSON → discount_amount, ...)
    - الحالة: status ∈ {pending, approved, rejected}, processed_by, processed_at
    - هذه هي الطبقة الوحيدة المخصصة لطلبات الاعتماد. لا يوجد نظام موافقات آخر.

  • workflow_fields / workflow_step_fields
    - يعرّف حقولاً ديناميكية مخصصة (visa_number, batch_no ... إلخ)
    - الربط: workflow_step_fields.step_id → field_id مع is_editable / is_visible / is_required

1.2 نظام الاعتماد (workflow_approvals.php)
--------------------------------------------------
الموقع: admin/workflow_approvals.php

  • يدعم نوعين من الطلبات:
      1) passport_id (معاملات الجوازات - قديم)
      2) booking_id (حجوزات باص/طيران - حديث)

  • آلية المعالجة عند الموافقة:
      1. فتح PDO transaction
      2. من جدول workflow_approval_requests جلب الطلب
      3. جلب to_step_id ثم إلى status_id عبر workflow_steps.status_id
      4. جلب بيانات الحجز + الفاتورة للحسابات المالية
      5. إذا كان extra_data.discount_amount > 0:
          - تحديث invoices.discount على الفاتورة الموحدة
          - حساب refund = amount_received - discount
          - إنشاء سند صرف (payment) عبر php_create_financial_entry
          - تحديث invoices.amount_received + payment_status
      6. تحديث bus_flight_bookings.status_id = to_status_id
      7. إذا اسم الحالة يحتوي "إلغاء" → ضبط cancel_datetime و is_cancelled
      8. استدعاء change_booking_status() لتسجيل السجل
      9. تحديث الطلب إلى status='approved', ضبط processed_by/processed_at/payment_id
     10. إدراج إشعار في جدول notifications للمستخدم المطلوب

  • عند الرفض: تحديث الحالة إلى 'rejected' مع إرسال إشعار بالرفض.

1.3 نظام الإشعارات الحالي
--------------------------------------------------
الجداول المعنية:
  • notifications (id, user_id, role_id, agent_id, branch_id, title, message, link,
                    source_type, source_id, type, is_read, created_by, created_at)
  • notification_settings (إعدادات إضافية إن وجدت)

مكان عرض الإشعارات:
  • في admin/header.php يوجد جرس إشعارات مركزي
  • العدادات المحسوبة:
      notif_count: عدد الإشعارات غير المقروءة للمستخدم الحالي
      unresolved_count: عملاء/فواتير مديونة
      expiry_count: تواريخ انتهاء وثائق قريبة
      unread_messages: رسائل contact_messages
      new_subscribers: مشتركين جدد
      unread_internal_count: رسائل داخلية
      pending_approvals_count: طلبات اعتماد معلقة (للمدراء فقط)
      total_alert_count = المجموع

  • دالة checkUpcomingTravelNotifications():
      - تضيف source_type, source_id إن لم تكن موجودة (Lazy Schema Alter)
      - توليد إشعارات لحجوزات الباص والطيران قبل 24 ساعة من المغادرة
      - توليد إشعارات لمعاملات الجوازات بنفس الطريقة
      - يمنع الازدواجية عبر فلتر (source_type, source_id)

1.4 صفحة الحجوزات bus_flight_bookings.php
--------------------------------------------------
الطبقات:
  • admin/bus_flight_bookings.php              الواجهة الرئيسية (جدول + نماذج + مودالات)
  • core/bookings/BookingWorkflowService.php  خدمة تغيير الحالات وطلبات الاعتماد
  • core/bookings/BookingCreatorService.php   إنشاء الحجز + الفواتير
  • core/bookings/BookingFinancialUpdater.php التحديثات المالية
  • core/bookings/BookingValidator.php        التحقق من صحة المدخلات
  • core/bookings/BookingServiceFactory.php   Factory حسب نوع الخدمة (bus/flight/combined)
  • includes/functions.php → change_booking_status() مركز تغيير الحالات

الأزرار الموجودة حالياً لكل سطر حجز:
  • requestCancelModal   → طلب إلغاء (يذهب إلى workflow_approvals)
  • requestModModal      → طلب تعديل (يذهب إلى workflow_approvals)
  • workflow dropdown    → الانتقالات المسموح بها مباشرة عبر change_workflow_status

جدول bus_flight_bookings الأعمدة ذات الصلة:
  • status_id ← مرتبط ب statuses.id
  • workflow_id (قابل للاستخدام، قيمته حالياً غالباً NULL)
  • confirm_datetime (تأكيد الحجز موجود!)
  • cancel_datetime / cancel_reason / is_cancelled (الإلغاء موجود!)
  • mod_datetime / mod_reason / requested_mod_date (التعديل موجود!)
  • ticket_number (رقم التذكرة موجود!)
  • invoice_id, sales_invoice_id, purchase_invoice_id

دالة change_booking_status() في includes/functions.php:
  • تتلقى: booking_ids, new_status_id, user_id, notes, extra_data[]
  • الأعمدة الإضافية المسموح تحديثها عبر extra_data[]:
      mod_reason, mod_datetime, requested_mod_date,
      cancel_reason, cancel_datetime, confirm_datetime,
      ticket_number, is_cancelled,
      وثائق أخرى خاصة بتأشيرات العمرة والعمل

  • تنشئ سجلاً في booking_status_logs (booking_id, old_status_id, new_status_id,
    changed_by, notes, created_at)

الفصل الثاني: تحليل المتطلبات الجديدة مقابل النظام الحالي

المتطلبات من المستخدم:

(1) نظام تأكيد الحجز
      أعمدة مقترحة: confirmed_at, confirmed_by, confirmation_method, is_confirmed
      والشرط: الربط مع Workflow الحالي وليس نظاماً مستقلاً.

    النتيجة التحليلية:
      ✅ الحجز يحتوي فعلياً على confirm_datetime وهو يعادل confirmed_at.
      ✅ booking_status_logs يحتوي changed_by أي أن confirmed_by يمكن استنتاجه منه.
      🔸 ناقص فقط confirmation_method (هاتف / واتساب / بريد / شخصي).
      ✅ الخطوة "تأكيد الحجز" موجودة كـ workflow_step (id=32).
      ✅ الانتقال 31→32 موجودة في workflow_transitions (require_approval=1).
      ✅ post_booking_to_financials مرتبط بـ trigger on_confirm عند الحاجة.
      ✅ BookingWorkflowService::confirmBooking موجود ويدعو change_booking_status.

    الخلاصة: لا نحتاج نظام تأكيد مستقل. نستخدم الانتقال في Workflow نفسه،
    ونضيف فقط:
      • عمود confirmation_method في جدول bus_flight_bookings (اختياري)
      • حقل workflow_field جديد (confirmation_method) نربطه بـ step_id=32 عبر
        workflow_step_fields مع is_required=true أو false حسب الرغبة.

(2) نظام تعديل الحجز
    الشرط: عدم وجود صفحة مستقلة، استخدام workflow_approvals.php فقط.

    النتيجة التحليلية:
      ✅ مودال طلب التعديل (requestModModal) موجود في bus_flight_bookings.php.
      ✅ BookingWorkflowService::requestApproval موجود ويُدخل الطلب مباشرة
        في جدول workflow_approval_requests.
      ✅ في workflow_approvals.php يتم معالجة الطلب وتطبيق discount_amount
        عبر البنية الموجودة بالفعل.
      ✅ change_booking_status يقبل extra_data['mod_reason', 'mod_datetime'].
      ⚠️ لكن: لا يوجد حتى الآن "آلية تطبيق التعديلات الفعلية على الحقول
          بعد الموافقة" (المسافر، الوجهة، التاريخ، السعر ...).
          الأن يتم فقط تطبيق الخصم والانتقال إلى status_name="تم تعديل الحجز".
      🔸 يحتاج:
          (a) أن نحفظ قِبَِل/بعد القيم في extra_data لطلب الاعتماد
              (توسيع existing JSON بدل إنشاء جدول جديد).
          (b) عند الموافقة في workflow_approvals.php، بعد تحديث الحالة،
              نطبق التغييرات على الحقول نفسها (مع فحص الصلاحيات لحقل
              مسموح بالتعديل في كل حالة عبر workflow_step_fields).

(3) نظام إلغاء الحجز والاسترداد المالي
    الشرط: الحفاظ على is_cancelled, cancel_reason, cancel_datetime الموجودة،
    وإرسال طلبات الإلغاء والاسترداد إلى workflow_approvals.php فقط.

    النتيجة التحليلية:
      ✅ cancel_reason, cancel_datetime, is_cancelled موجودة بالفعل في الجدول.
      ✅ زر طلب الإلغاء موجود (requestCancelModal).
      ✅ في workflow_approvals.php عند الموافقة على طلب الإلغاء:
          • يتم احتساب الغرامة discount_amount
          • إنشاء سند صرف (استرداد) عبر php_create_financial_entry
          • تحديث الفاتورة (amount_received, payment_status)
          • ضبط is_cancelled=1 و cancel_datetime=NOW()
      🔸 ما هو ناقص جزئياً:
          (a) ربط workflow_steps بكل عملية (خطوة تأكيد → خطوة إلغاء)
              مع تحديد هل الانتقال يحتاج اعتماد أم لا (متاح حالياً في
              workflow_transitions.require_approval).
          (b) توحيد مسار "إلغاء مباشر بدون موافقة" إلى مسار موحد
              عبر الطبقة نفسها (BookingWorkflowService) لا التوزيع على
              أكثر من كود مسار.

(4) إشعارات الحجوزات
    الشرط: عدم وجود صفحة جديدة، استخدام نظام الإشعارات الحالي (جرس الـ header

    النتيجة التحليلية:

      ✅ checkUpcomingTravelNotifications يرسل تنبيهات موعد الرحلة.
      🔸 نحتاج فقط إلى:

الحالة أ: تأكيد الحجز
---------------------
المحفز: المستخدم ينقر على زر الانتقال إلى "تأكيد الحجز" من dropdown الـ workflow
أو يملأ مودال تأكيد الحجز.

الخطوات التنفيذية في النظام الحالي (بعد التطوير المقترح):

1. [الواجهة - bus_flight_bookings.php]
   المستخدم يختار الانتقال 31→32 (جديد → تأكيد الحجز)
   → يفتح Modal خاص بالانتقال يعرض الحقول المرتبطة بالخطوة المستهدفة
   (confirm_datetime, ticket_number, confirmation_method)
   يتم جلب هذه الحقول عبر workflow_step_fields لـ step_id=32.

2. [التحقق]
   if (workflow_transitions.require_approval == 1)   // TRUE حالياً للانتقال 31→32
     → بدلاً من تغيير الحالة مباشرة، يتم إرسال الطلب إلى
       BookingWorkflowService::requestApproval(booking_id, to_step_id=32, discount=0, notes).
       → يدرج صفاً في workflow_approval_requests مع extra_data JSON يحوي
         القيم المدخلة لحقول خطوة التأكيد (confirm_datetime, ticket_number,
         confirmation_method).

3. [إشعار فوري]
   notifyApprovalTargets: إشعار للمدراء في notifications مع
   type='warning' و link='workflow_approvals.php?status=pending'.

4. [صفحة الاعتماد - workflow_approvals.php]
   عند المعالجة:
   a. جلب extra_data → القيم المؤقتة لحقول التأكيد.
   b. التحقق من الحقول is_required=true عبر workflow_step_fields.
   c. إذا was_transition.require_approval=1 بالفعل:
        change_booking_status(booking_id, to_status_id, processor_id, notes,
                              extra_data = [confirm_datetime, ticket_number,
                                            confirmation_method, is_confirmed=1,
                                            confirmed_by=processor_id])
   d. تفعيل auto_action إن وجد (supplier_credit_posting) أو استدعاء
      post_booking_to_financials حسب الإعدادات.
   e. تحديث workflow_approval_requests إلى 'approved'.
   f. إرسال إشعار نجاح إلى user_id المطلوب في notifications مع
      source_type='booking_confirm' و source_id=booking_id.

5. [في حالة انتقال لا يحتاج اعتماد]:
   → يتم كل شيء فوراً في changeWorkflowStatus دون المرور بطلب اعتماد.


الحالة ب: تعديل الحجز
---------------------
المحفز: المستخدم يضغط زر "طلب تعديل" (القلم الأصفر) في جدول الحجوزات.

الخوارزمية المقترحة (استخدام البنية الحالية بدون صفحة جديدة):

1. [الواجهة - requestModModal]
   Modal يطلب من المستخدم إدخال:
      • السبب (mod_reason)
      • قائمة الحقول المراد تعديلها (dropdown من الحقول المسموح تعديلها في
        المرحلة الحالية - يمكن إحضارها من workflow_step_fields.is_editable=1
        على الخطوة الحالية).
      • لكل حقل: القيمة القديمة + القيمة الجديدة (عرض الجانبي).
      • الغرامة المقترحة (discount_amount) إن وجدت.

2. [الإرسال إلى النظام]
   BookingWorkflowService::requestApproval(booking_id, to_step_id=34,
                                            discount_amount, notes).
   لكن هذه المرة extra_data يحوي بالإضافة إلى discount_amount مفتاحاً جديداً
   يسمى changes = {
       field_name: {old: .., new: ..}
   }.
   هذا التوسيع في نفس JSON الحالي دون جدول جديد.

3. [اعتماد المدير في workflow_approvals.php]
   عند الموافقة على الطلب الذي to_step_id يعادل خطوة "تم تعديل الحجز":
     a. جلب extra_data['changes'].
     b. لكل field_name:
        - التحقق من أن الحقل موجود في قائمة الحقول المسموح بتعديلها
          (مثل is_editable في خطوة الحالة الحالية أو قائمة بيضاء ثابتة
           من أعمدة bus_flight_bookings).
        - تحديث القيمة في جدول bus_flight_bookings (فقط الحقول المسموح بها
          مثل: requested_mod_date, traveler_name - إن سمحنا -، mobile_number،
          departure_date، return_date، notes، إلخ).
     c. تطبيق discount_amount عبر البنية الموجودة (خصم الفاتورة وإنشاء
        سند صرف إن لزم).
     d. تحديث status_id إلى status_id لخطوة "تم تعديل الحجز".
     e. استدعاء change_booking_status مع extra_data mod_reason, mod_datetime.
     f. إرسال إشعار بنجاح التعديل إلى notifications.

4. إذا تم رفض الطلب: يتم فقط تحديث حالة workflow_approval_requests إلى
   'rejected' مع إرسال إشعار بالرفض.


الحالة ج: إلغاء الحجز والاسترداد المالي
-----------------------------------------
المحفز: زر "طلب إلغاء" (requestCancelModal).

الخوارزمية:

1. [الواجهة]
   المستخدم يدخل: سبب الإلغاء (cancel_reason)، ونسبة أو مبلغ الغرامة
   (discount_amount)، وتاريخ الإلغاء (يأخذ تلقائياً الآن).

2. [النقل إلى خدمة الاعتماد]
   BookingWorkflowService::requestApproval(booking_id, to_step_id=33,
                                            discount_amount, notes=cancel_reason).
   يتم إدراج الطلب في workflow_approval_requests.

3. [workflow_approvals.php عند الموافقة]
   a. التحقق: if اسم الحالة يحتوي "إلغاء" → يُعّد is_cancelled = 1 و
      cancel_datetime = NOW() و cancel_reason = notes.
   b. يتم الاستفادة من discount_amount الموجودة في النظام الآن:
       • discount على الفاتورة
       • refund = amount_received - discount
       • إنشاء سند صرف (استرداد) عبر php_create_financial_entry إن refund>0
       • تحديث amount_received و payment_status في الفاتورة
   c. تحديث booking_status إلى status_id إلغاء الحجز عبر change_booking_status.
   d. تحديث payment_id في workflow_approval_requests لسند الصرف الذي
      تم إنشاؤه.
   e. إشعار بنجاح الإلغاء وإن وجد مبلغ استرداد في notifications.

4. [في الرفض] → نفس مسار الرفض العام.


الحالة د: إصدار التذكرة الرقمية
-------------------------------
المحفز: زر "تذكرة" (عرض / طباعة / PDF / QR) داخل سطر الحجز.

الآلية المقترحة:

1. [شرط الظهور]
   function is_ticket_available(booking):
     a. الحالة الحالية status ∈ الخطوات المؤهلة.
        طريقة بسيطة: أن يكون status_id من خلال workflow_steps التي
        step_key IN ('confirm', 'ticket_issued') أو نضيف عموداً واحداً
        في workflow_steps باسم is_ticketable (TINYINT) نعدّله من صفحة
        workflow.php الحالية.
     b. وجوب ticket_number أو وجود قيمة confirm_datetime.

2. [التأكد من الحقول المطلوبة في خطوة "إصدار التذكرة" إن وجدت]
   تحقق من workflow_step_fields للحقل (مثل flight_number, seat_number...)
   قبل السماح بإنشاء التذكرة.

3. [الأزرار] داخل سطر العمليات في bus_flight_bookings.php:
   • <a href="print_ticket.php?id=X" target="_blank">
       <i class="fa fa-eye"></i> عرض التذكرة
     </a>
   • <a href="print_ticket.php?id=X&format=pdf" target="_blank">
       <i class="fa fa-file-pdf"></i> PDF
     </a>
   • <a href="#" onclick="printTicket(X)">طباعة</a>
   • زر QR يعرض Popup يحتوي صورة QR للـ ticket_number.

4. [الملف الجديد - مكوّن طباعة لا صفحة]
   اسم الملف المقترح: admin/ticket_view.php (أو admin/print_ticket.php)
   يقبل id=booking_id، ويقرأ بيانات الحجز + العميل + التفاصيل المالية
   ويعرضها في قالب Print Format (CSS print-ready).
   مع رابط تنزيل PDF (يمكن استخدام مكتبة مثل Dompdf أو TCPDF تحمل محلياً
   في مجلد tools/libs).

5. [توليد إشعار]
   عند أول فتح للتذكرة أو إصدارها: إدراج إشعار واحد في notifications
   مع source_type='booking_ticket_issued', source_id=booking_id
   (يمنع الازدواجية عبر فحص سابق للـ source_type + source_id).


الحالة هـ: التذكير بالرحلة
---------------------------
الموجود فعلياً حالياً: دالة checkUpcomingTravelNotifications تتحقق من
الحجوزات التي departure_date بين اليوم وغداً، وتدرج إشعاراً إن لم يكن
موجوداً مسبقاً بـ source_type+source_id.

كل نحتاج فقط توسيعها لتشمل:
  • X أيام قبل المغادرة (تكون configurable من الإعدادات).
  • إشعار قبل 3 أيام + إشعار في يوم المغادرة.
  • إشعار عند صدور التذكرة (كما في الحالة د).

كل ذلك ضمن نفس جدول notifications وبدون أي واجهات جديدة.

4.1 الجداول المستخدمة بدون أي تغيير

4.2 التوسيعات على الجداول الحالية (ALTER TABLE Add Columns فقط)
  ■ جدول: bus_flight_bookings
    • is_confirmed          TINYINT(1) DEFAULT 0    (لتوحيد التحقق)
    • confirmed_by          INT(11)        NULL    (FK → users.id، يملأ بعد
                                                    الموافقة على التأكيد)
    • confirmation_method   VARCHAR(50)    NULL    ('phone','whatsapp',
                                                    'email','in_person',
                                                    'system_auto')

    السبب: هذه الأعمدة الأربعة تكمل دقة عملية التأكيد، والـ confirmed_by
    هو اختصار لعدم الحاجة للبحث في booking_status_logs في كل تقرير.
    يمكن التخلي عن confirmed_by والاعتماد على logs، لكنه يوفر استعلامات
    تقارير أسرع. إذا رفض المستخدم إضافة أعمدة → نكتفي بـ confirm_datetime
    الموجودة حالياً ونستخرج الباقي من logs + JSON.

  ■ جدول: workflow_steps
    • is_ticketable   TINYINT(1) DEFAULT 0
    السبب: هو الطريقة الأنظف لتحديد أي خطوات Workflow تسمح بإصدار
    تذكرة رقمية، يمكن التحكم بها من صفحة workflow.php.
    إذا رفض المستخدم إضافة هذا العمود → نستخدم قائمة بيضاء ثابتة لـ
    step_keys (مثل 'confirm') داخل الكود.

4.3 هل نحتاج جداول جديدة؟
  ⚠️ الإجابة: لا، لا نحتاج لأي جدول جديد للمتطلبات الستة السابقة.

  • تأكيد الحجز → توسيع أعمدة بسيطة في bus_flight_bookings +
    استخدام workflow_transitions و workflow_approval_requests الموجودة.

  • تعديل الحجز → تستخدم workflow_approval_requests.extra_data كحاوية
    JSON لحفظ {old/new changes}. لا جدول مستقل.

  • إلغاء الحجز والاسترداد → كل شيء موجود: is_cancelled, cancel_reason,
    cancel_datetime, payment_id في workflow_approval_requests و
    الفواتير وسندات القبض/الصرف عبر php_create_financial_entry.

  • إشعارات الحجوزات → جدول notifications موجود بالكامل مع source_type
    و source_id و user_id / role_id / agent_id / branch_id.

  • التذاكر الرقمية → داخل bus_flight_bookings + ملف عرض واحد. لا جدول جديد
    بغرض حفظ التذاكر. إذا احتجنا لاحقاً إلى تسلسل issuance نسخة 2/3 يمكن
    استخدام ticket_number الموجود وتواريخ التحديث.

4.4 إدخال صفوف جديدة في جداول الإعدادات فقط (INSERT غير DDL):
  • workflow_fields: إضافة حقل 'confirmation_method' إن لم يكن موجوداً
    مع field_type='select' و options JSON يحتوي على طرق التأكيد.
  • workflow_step_fields: ربط confirmation_method بـ step_id الخاص
    بـ "تأكيد الحجز" (step_id=32) مع is_required حسب الرغبة.
  • يمكن إضافة حقول إضافية مثل 'flight_seat', 'flight_gate',
    'ticket_class' لتظهر في خطوة إصدار التذكرة إن لزم.

5.2 ضمان عدم تكرار الوظائف

  ✅ لا يتم إنشاء نظام تأكيد مستقل. التأكيد هو مجرد transition ضمن
     سير العمل، كما هو معمول به الآن ولكنه أصبح أكثر تفصيلاً.

  ✅ لا يتم إنشاء نظام موافقات جديد. كل الطلبات تذهب إلى نفس
     workflow_approval_requests و workflow_approvals.php.

  ✅ لا يتم إنشاء نظام إشعارات جديد. كل الإشعارات تذهب إلى نفس
     notifications ويظهر في جرس الـ header.

  ✅ لا يتم إنشاء صفحة تذاكر منفصلة. الأزرار داخل صفحة الحجوزات نفسها
     ويتم استدعاء مكوّن عرض/طباعة من نفس السياق.

  ✅ لا يتم إنشاء Workflow جديد. سير عمل الحجوزات الحالي (workflow_id=5)
     هو الذي نطوّر خطواته وحقوله فقط.
